# NodeSummary 认知模型 - 一致性设计文档

## 一、设计理念

本文档定义了跨三种视图（Card/List/Topology）的统一 **NodeSummary 认知模型**，确保用户在任何视图中都能建立对节点的一致认知，而不需要反复切换页面拼凑信息。

---

## 二、NodeSummary 核心结构

NodeSummary 是用户在不进入详情页时，对一个节点的 **最小充分认知集合**。

### 1️⃣ 身份 (Identity)

| 字段 | 说明 | 显示位置 |
|-----|------|---------|
| `node_name` | 节点名称 | 所有视图主标题 |
| `user_name` | 所属用户 | Card 分组头 / List Tooltip |

### 2️⃣ 状态 (State) - 两个独立维度

| 维度 | 字段 | 含义 | 显示方式 |
|-----|------|------|---------|
| **节点状态** | `node_status` | 节点配置状态<br>-1=配置不完整<br>0=已禁用<br>1=启用但未上线<br>2=在线 | 芯片：红/灰/橙/绿 |
| **链路状态** | `online` | 当前连接是否活跃 | 芯片："链路在线"/"链路离线"<br>带 link/link_off 图标 |

⚠️ **关键理解**：
- `node_status` 反映节点自身的配置状态（来自 `nodes_metadata`）
- `online` 反映当前网络链路的连通性（来自 `connections.online`）
- 两者并存且独立：节点可以"在线"但链路"离线"，反之亦然

### 3️⃣ 网络信息 (Network)

| 字段 | 说明 | 图标 | 显示优先级 |
|-----|------|------|----------|
| `virtual_ip` (node_ip) | 虚拟隧道IP | `vpn_key` | 必显 (主) |
| `wanip` | 公网IP | `public` | 必显 (次) |
| `latency` | 延迟 (ms) | `speed` | 链路在线时显示 |
| `conn_type` | 连接类型 | - | 链路在线时显示 |
| `lan_ip` | 局域网IP | `home` | 次要信息，可折叠 |

## 三、三种视图的信息层次分工

### Card 视图 - 快速扫视

**目标**：一眼判断节点可用性

**信息布局**：
```
┌────────────────────────────────────┐
│ 👤 用户分组 (每组首条显示)         │
├────────────────────────────────────┤
│ 🔷 节点名称                        │
│ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━│
│ [节点状态]  [链路在线/离线]        │ ← 一行双芯片
│ 🔑 10.x.x.x  |  🌐 192.x.x.x      │ ← 紧凑IP展示
│ ⚡ 25.3ms  直连 IPv4 (仅在线时)   │ ← 次要信息
│ 📂 局域网地址 (可展开)             │
└────────────────────────────────────┘
```

**优化点**：
- 状态芯片合并到一行
- IP 信息紧凑展示（图标 + 值 + 分隔符）
- 次要信息（延迟/连接类型）仅在链路在线时显示
- LAN IP 折叠展示

### List 视图 - 横向对比

**目标**：单行完成判断，对比友好

**列结构**：
```
| 节点名称     | 虚拟IP        | 公网IP        | 节点状态  | 链路状态  | 延迟    | 流量    | 最后通信 | 操作 |
|-------------|--------------|--------------|----------|----------|---------|---------|---------|------|
| 🔷 Node-A   | 🔑 10.1.1.1  | 🌐 1.2.3.4   | [在线]   | [在线]   | 25.3ms  | ↓↑      | 2分钟前 | 👁   |
| 🔷 Node-B   | 🔑 10.1.1.2  | —           | [启用]   | [离线]   | N/A     | —       | 1小时前 | 👁   |
```

**优化点**：
- 节点名称单行展示，用户名移至 Tooltip
- IP 列不使用 chip，改为图标+文本（节省空间）
- 状态列使用 chip 但保持 compact
- 离线链路用 outline chip + 灰色

### Topology 视图 - 关系感知

**目标**：Hover 即获得完整 NodeSummary

**Tooltip 结构**：
```
┌─────────────────────────────────┐
│ 节点名称: Node-A                │ ← 身份
├─────────────────────────────────┤
│ 节点状态: [在线]                │ ← 状态维度1
│ 链路状态: [🔗 链路在线]         │ ← 状态维度2
├─────────────────────────────────┤
│ 🔑 虚拟 IP: 10.1.1.1           │ ← 网络信息
│ 🌐 公网 IP: 1.2.3.4            │
├─────────────────────────────────┤
│ 延迟: 25.3 ms                   │ ← 次要信息
│ 流量: ⬇ 1.2MB ⬆ 500KB         │   (仅在线时)
├─────────────────────────────────┤
│ 最后通信: 2分钟前               │ ← 时间信息
└─────────────────────────────────┘
```

**优化点**：
- 按 NodeSummary 三层结构组织信息
- 分隔线划分层次
- 次要信息仅在链路在线时显示
- 图标与文本语义一致

## 四、命名一致性规范

### ✅ 统一术语

| 概念 | 字段名 | 中文显示 | 英文显示 |
|-----|--------|---------|---------|
| 节点状态 | `node_status` | "在线"/"启用但未上线"/"已禁用" | Online/Enabled/Disabled |
| 链路状态 | `online` | "链路在线"/"链路离线" | Link Online/Link Offline |
| 虚拟IP | `node_ip` / `virtual_ip` | "虚拟 IP" | Virtual IP |
| 公网IP | `wanip` | "公网 IP" | WAN IP |

### ❌ 避免的术语

| 不应使用 | 原因 | 应改为 |
|---------|------|--------|
| "连接在线/离线" | 与 `node_status` 混淆 | "链路在线/离线" |
| "连接状态" | 歧义（是节点还是链路？） | 明确说"链路状态" |
| "节点IP" | 不明确（虚拟还是公网？） | "虚拟 IP" 或 "公网 IP" |

## 五、颜色与图标一致性

### 状态颜色

| 状态 | 颜色 | 使用场景 |
|-----|------|---------|
| node_status=2 (在线) | `positive` (绿) | 节点状态芯片 |
| node_status=1 (启用未上线) | `orange` (橙) | 节点状态芯片 |
| node_status=0 (禁用) | `grey` (灰) | 节点状态芯片 |
| node_status=-1 (不完整) | `negative` (红) | 节点状态芯片 |
| online=true | `positive` (绿) | 链路状态芯片 |
| online=false | `grey-6` + outline | 链路状态芯片 |

### 图标映射

| 信息类型 | 图标 | 颜色 |
|---------|------|------|
| 节点 | `router` | `primary` |
| 虚拟IP | `vpn_key` | `primary` |
| 公网IP | `public` | `secondary` |
| 局域网IP | `home` | `accent` |
| 链路在线 | `link` | - |
| 链路离线 | `link_off` | - |
| 延迟 | `speed` | - |

## 六、数据源映射

### API 响应结构
```json
{
  "connections": [
    {
      "peer_id": "xxx",
      "online": true,          // ← 链路状态
      "wanip": "1.2.3.4",      // ← 公网IP
      "latency": 25.3,
      "conn_type": "direct_ipv4",
      "seen_at": "2025-12-21T..."
    }
  ],
  "nodes_metadata": {
    "peer_id": {
      "node_status": 2,        // ← 节点状态
      "node_ip": "10.1.1.1",   // ← 虚拟IP (首选)
      "ip_addresses": [
        { "ip_address": "10.1.1.1", "route_type": "node_ip" },
        { "ip_address": "192.168.1.x", "route_type": "lan_ip" }
      ]
    }
  }
}
```

### 字段获取逻辑
```typescript
// ✅ 正确
const nodeStatus = nodesMetadata[peerId].node_status   // 从 metadata 读
const linkStatus = connection.online                    // 从 connection 读
const virtualIp = nodesMetadata[peerId].node_ip        // 优先 node_ip
const wanIp = connection.wanip                          // 从 connection 读

// ❌ 错误
const nodeStatus = connection.peer_node_status         // ❌ connection 里没这字段！
const linkStatus = (connection.conn_type !== 'offline') // ❌ 不要重新计算，API已计算
```

## 七、用户认知检验标准

### ✅ 成功标准

用户应该能够：

1. **一眼区分**节点配置状态 vs 当前连接状态
   - "这个节点已启用但暂时离线" ✓
   - 而非 "这个节点到底在不在线？" ✗

2. **不切换视图也能获取关键信息**
   - Card 视图："Node-A 链路在线，虚拟IP 10.1.1.1，公网IP 1.2.3.4" ✓
   - List 视图：同一节点显示相同状态和IP ✓
   - Topology 视图：Hover 获得完整 NodeSummary ✓

3. **跨视图信息一致**
   - Card 显示"链路在线"，List 也显示"链路在线"，Topology tooltip 同样 ✓
   - 颜色、图标、术语保持一致 ✓

### ❌ 反面案例

- "为什么这里显示在线，那里显示离线？" ← 数据来源不一致
- "连接状态和节点状态有什么区别？" ← 命名不清晰
- "这个IP是虚拟IP还是公网IP？" ← 标签缺失

## 八、实施边界

### ✅ 可以做的
- 调整信息展示顺序和布局
- 合并/拆分现有 UI 区块
- 增加 Tooltip / Hover 信息
- 优化颜色/图标语义

### ❌ 不需要做的

- 改变路由结构
- 重构整体架构

---

## 九、维护指南

当需要新增字段或调整展示时，请按以下步骤检查：

1. **确认信息层级**：属于身份/状态/网络哪一类？
2. **检查命名一致性**：三个视图是否使用相同术语？
3. **验证数据源**：来自 `connections` 还是 `nodes_metadata`？
4. **测试跨视图一致性**：同一节点在三个视图中信息是否吻合？
5. **用户认知测试**：是否会产生"拼信息"的需求？

> 不是让三种视图完全一样，而是让它们基于同一套认知模型各司其职。
